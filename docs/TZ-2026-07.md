## 0. Цель и метрики успеха

**Цель:** за 8–12 недель превратить ReelPay из готового демо в живую платформу №1 РФ-клиппинга:
единственную с self-serve эскроу-визардом, автоматической проверкой просмотров, белой юридикой
(ЕРИР + самозанятость) и обеими воронками роста (TG + SEO).

| Метрика | Цель |
|---|---|
| Время от создания кампании до первого опубликованного клипа | < 48 ч |
| Задержка обновления просмотров | ≤ 30 мин (сейчас — сутки) |
| Выплата клипперу после порога | 48 ч холда, далее автоматически (сейчас — вручную) |
| Доля кампаний, запущенных заказчиком без менеджера | 100% (self-serve) |
| Рекламные кампании с erid | 100% |
| SEO: страниц в индексе через 3 мес | 50+ (лендинг, кампании, профили, блог) |

**Приоритеты:** P0 — без этого не запускаемся; P1 — конкурентные дифференциаторы первых недель;
P2 — рост и масштаб.

## 1. Юридика: ЕРИР/ОРД и права на контент (P0/P1) — раздел составлен вручную

### 1.1. Автоматическая маркировка рекламы (erid) — P1
1. **Модель данных:** миграция — поля на `Campaign`: `isAdvertising Boolean @default(true)`,
   `erid String?`, `ordProvider String?`, `advertiserInn String?`, `advertiserName String?`,
   `ordRegisteredAt DateTime?`. Кампании-«не реклама» (собственный контент стримера про себя)
   помечаются `isAdvertising=false` с обязательным подтверждением-чекбоксом заказчика.
2. **Интеграция ОРД:** модуль `lib/ord.ts` — интерфейс `OrdProvider` (регистрация креатива →
   erid; передача статистики показов), первый адаптер — ОРД VK или МедиаСкаут (у обоих REST API;
   конфиг через env `ORD_PROVIDER`, `ORD_API_KEY`). Mock-провайдер для дев-среды.
3. **Поток:** визард кампании собирает ИНН/название рекламодателя → при публикации рекламной
   кампании создаётся креатив в ОРД → erid сохраняется → **erid и пометка «Реклама. <Наименование>.
   erid: XXX» автоматически добавляются в требования кампании** (текст, который клиппер обязан
   разместить в описании ролика рядом с tracking-кодом).
4. **Проверка:** `lib/antifraud.ts` (проверка tracking-кода) расширяется проверкой наличия erid
   в описании публикации для рекламных кампаний — тот же механизм, что tracking-код; отсутствие
   erid = блокер выплаты со статусом «нет маркировки».
5. **Отчётность:** ежемесячная передача статистики показов в ОРД (route
   `/api/maintenance/ord-report`, cron) — v1 допустима ручная выгрузка CSV в админке.
6. **DoD:** рекламная кампания не может быть опубликована без erid (или явного `isAdvertising=false`);
   клип без erid в описании не проходит верификацию; в админке виден статус маркировки кампаний.

### 1.2. Права на контент — P1
1. Оферта (app/legal/terms): заказчик получает неисключительную лицензию на использование
   принятых клипов (включая рекламу и перезалив) с момента выплаты; клиппер сохраняет авторство;
   отдельные опции кампании: «эксклюзив» и «запрет AI-обучения» (по образцу Billo) — платные флаги
   (поля `licenseExclusive Boolean`, `allowAiTraining Boolean` на Campaign, миграция).
2. Карточка кампании показывает блок «Права на контент» (что получает заказчик, что остаётся
   клипперу) — как у Insense «Payments & Copyrights».
3. **DoD:** в каждом заказе явно виден режим прав; текст оферты обновлён; чекбокс-акцепт брифа
   фиксирует согласие с правами (см. раздел «Модерация», задача про briefVersion).

### 1.3. Правовой статус seed-кампаний — P1
Кампании «Организовано ReelPay» с контентом стримеров: обязательное письменное согласие
правообладателя исходника (шаблон-соглашение), маркировка по правилам 1.1, если содержит рекламу
третьих лиц. Не копировать уловку Клипни «это не реклама» без анализа.

## 4. Синк каждые 15 минут, прозрачный антифрод, публичный отчёт (P0–P1)

### 4.1. Частый синк через внешний триггер
- **Создать** `.github/workflows/sync-views.yml`: `schedule: '*/15 * * * *'` → `curl -X POST
  $PROD_URL/api/sync/views -H "Authorization: Bearer $CRON_SECRET"` (секреты в GitHub). GitHub
  Actions выбран вместо QStash: бесплатно, без новой зависимости, ±5 мин точности достаточно.
  Cron в `vercel.json` (03:00) оставить как фоллбек полного прогона.
- В route добавить: (а) advisory-lock от параллельных запусков —
  `SELECT pg_try_advisory_lock(hashtext('sync_views'))` в начале, unlock в finally; при занятом
  локе — 200 с `{skipped:true}`; (б) параметр батча: за прогон максимум N=50 submissions,
  приоритет статусов SETTLING > THRESHOLD_MET > VERIFIED > POSTED, внутри — `lastSyncedAt` старше
  15 мин (индекс по status+lastSyncedAt — проверить/добавить в миграции); (в) запись длительности
  и объёма в AuditLog.
- Бюджет квот: YouTube Data API 10 000 units/день ≈ 10 000 videos.list; 50 × 96 прогонов =
  4 800/день — в лимите. VK service token — лимиты выше.

### 4.5. Привязка соцаккаунтов: безопасно, несколько способов, рекомендуется (не принуждается)

Цель: клиппер с привязанным аккаунтом сдаёт ссылки **без tracking-кода в описании** — владение
подтверждается автоматически сверкой «видео ↔ подтверждённый аккаунт». Код остаётся fallback'ом.
Модель `SocialAccount` уже есть (токены шифруются AES-256-GCM, `lib/secret-box.ts`); TikTok-путь
через OAuth уже подтверждает принадлежность видео (`lib/social-platforms.ts`, video.list).

1. **Модель данных.** Миграция `SocialAccount`: `verificationMethod String?` (`OAUTH|CODE|MANUAL`),
   `externalAccountId String?` (channelId YouTube / owner_id VK / open_id TikTok),
   `accountUrl String?`, уникальный индекс `(platform, externalAccountId)` — один реальный аккаунт
   нельзя привязать к двум профилям ReelPay (анти-«аренда» аккаунтов).
2. **Способ 1 — OAuth (рекомендуемый, ноль действий дальше).** Расширить существующий флоу
   `app/api/social/oauth/[platform]` на YouTube (Google, scope `youtube.readonly`; заявка на
   верификацию приложения Google — отдельная операционная задача с чек-листом) и VK (VK ID).
   TikTok уже работает. После подключения сохраняем `externalAccountId`, `verificationMethod=OAUTH`.
3. **Способ 2 — верификация кодом, один раз на аккаунт (для тех, кто не хочет OAuth).** Экран
   «Добавить аккаунт по ссылке»: клиппер вводит URL канала → получает код `RP-XXXXXX` → вставляет
   в описание канала/био (или описание любого своего видео) → «Проверить» → система читает
   публичным API (YouTube channels.list / VK groups.getById|users.get) → `verifiedAt`,
   `verificationMethod=CODE`, `externalAccountId`. Код живёт 24 ч, после проверки его можно
   удалить. Лимит: 5 попыток/час (существующий `lib/rate-limit.ts`).
4. **Способ 3 — как сейчас (fallback).** Без привязки: tracking-код на каждое видео; Instagram —
   код + ручная модерация. Ничего не ломаем.
5. **Проверка владения становится стратегией** (`lib/antifraud.ts`): (а) `externalAccountId`
   видео совпадает с верифицированным аккаунтом клиппера → OWNERSHIP PASS, ре-проверки кода не
   нужны (принадлежность видео аккаунту неизменна); (б) иначе — текущий путь tracking-кода;
   (в) иначе — NEEDS_REVIEW. Юнит-тесты на все три ветки.
6. **Безопасность:** токены — только шифрованные (уже так); при отвязке аккаунта активные работы
   продолжают проверяться по сохранённому `externalAccountId`, не по токену; каждая привязка/
   отвязка — в AuditLog; env-флаг аварийного отключения OAuth-путей; scope-минимализм (только
   чтение). Страница /safety/views дополняется абзацем «что мы видим при подключении аккаунта,
   а что — нет» (не видим переписку, не можем публиковать).
7. **UX мягкой рекомендации (не принуждение):** шаг онбординга клиппера «Подключите соцсети»
   с кнопкой «Пропустить» (как у Клипни, но необязательный); баннер в /upload «Подключи аккаунт —
   сдавай ссылки без кодов»; бейдж «Аккаунт подтверждён» в профиле и портфолио; при сдаче ссылки
   с подтверждённого аккаунта — зелёная строка «владение подтверждено автоматически».
8. **Опция для строгих заказчиков:** `Campaign.requireVerifiedAccount Boolean @default(false)`
   (миграция) — чекбокс в визарде «принимать отклики только от клипперов с подтверждёнными
   аккаунтами»; фильтр в матчинге (`lib/campaign-matching`).
- **DoD:** клиппер с привязанным аккаунтом проходит ownership без кода конец-в-конец (e2e);

  аудитории стримера. Две seed-кампании в первый месяц после запуска выплат.
- **DoD:** бейдж отображается; в админке фильтр по isPlatformOrganized; юр-требования — раздел 1.3.

## 7. Техническая гигиена (P2, фоном)
1. CI: GitHub Actions — lint + typecheck + unit (единый `npm test`, собрать все tests/*.test.mts)
   + e2e на PR (отдельная job с Postgres-сервисом и схемой reelpay_e2e из playwright.config.ts).
2. Починить `npm run lint`: миграция с удалённого `next lint` на ESLint CLI
   (`npx @next/codemod@canary next-lint-to-eslint-cli`).
3. Распил `app/actions.ts` (~1900 строк) по доменам (campaigns/wallet/disputes/drafts) без смены
   поведения; продолжение миграции globals.css (14 700 строк) на CSS Modules — только для секций,
   которые трогаем в этом ТЗ.
4. CHECK-инварианты в БД: `balanceCents >= 0`, `holdBalanceCents >= 0`,
   `remainingBudgetCents >= 0`, `reservedBudgetCents >= 0` (raw SQL миграция).
5. `sessionVersion` на User для инвалидации сессий при смене пароля.
