# Выдержит ли сайт 1000 человек — как это узнать точно

Нагрузку в 1000 одновременных пользователей нельзя проверить «на глаз» или из среды
разработки — только реальным тестом против задеплоенного прод-URL, потому что всё упирается
в реальную базу данных и serverless-инфраструктуру. Ниже — что уже сделано в коде для масштаба,
что проверить руками, и как получить точные цифры.

## 1. Что в коде уже готово к нагрузке

- **Пул соединений с БД.** `DATABASE_URL` идёт через pgBouncer с `connection_limit=1`
  (`.env.example`), `DIRECT_URL` — только для миграций. Это правильная схема для serverless:
  тысяча параллельных функций не открывают тысячу прямых соединений к Postgres.
- **Один PrismaClient на инстанс** (`lib/prisma.ts`) — не создаётся заново на каждый запрос.
- **Кэш горячих чтений.** Лента кампаний и лидерборд кэшируются (`unstable_cache`, ~30 сек),
  так что пик читателей не бьёт по БД на каждый запрос.
- **Атомарные записи денег** (условные `updateMany`, транзакции) — конкурентные операции не
  портят балансы даже под нагрузкой.
- **Keepalive-крон каждые 5 минут** держит Neon «тёплым» (меньше холодных стартов).

## 2. Что проверить руками ПЕРЕД тестом (это и есть настоящие лимиты)

Код готов, но потолок задаёт инфраструктура. Проверь в проде:

1. **Прод `DATABASE_URL` реально пулится?** Должен содержать `pgbouncer=true&connection_limit=1`
   (Neon: строка с хостом `...-pooler...`). Без этого 1000 юзеров исчерпают соединения → 500.
2. **План БД (Neon/Supabase).** Бесплатный тариф ограничивает число соединений и compute.
   Для 1000 активных нужен платный тариф с pooler'ом.
3. **Upstash Redis подключён?** (`UPSTASH_REDIS_REST_URL/TOKEN`) — без него rate-limit работает
   послаблено (по инстансам). Не уронит сайт, но защита от абьюза слабее.
4. **План Vercel.** Hobby ограничивает конкурентность функций и время; для 1000 юзеров — Pro.

## 3. Запуск нагрузочного теста

```bash
# 1. Установить k6 (Windows):
winget install k6
# 2. Мягкий прогон — 200 пользователей (убедиться, что всё живо):
k6 run -e BASE_URL=https://ВАШ-ПРОД-URL -e PEAK=200 scripts/loadtest.js
# 3. Полный прогон — 1000 пользователей:
k6 run -e BASE_URL=https://ВАШ-ПРОД-URL scripts/loadtest.js
```

Тест 4 минуты: разгон до пика, 2 минуты удержания 1000 виртуальных пользователей, спад.

## 4. Как читать результат

k6 в конце покажет:
- **`http_req_failed`** — доля ошибок. Порог в тесте: **< 1%**. Если больше — смотри, на каком
  пути (обычно `/campaigns`) и в логах Vercel/Neon (чаще всего «too many connections»).
- **`http_req_duration p(95)`** — 95% запросов быстрее этого. Порог: **< 1.5 сек**.
- **`✓ status is 200`** — доля успешных.

Итог `✓ thresholds crossed` (все зелёные) = **1000 пользователей сайт держит**.
`✗` на `http_req_failed` = упирается в БД/план — см. пункт 2.

## 5. Чего этот тест НЕ покрывает

- Только гостевые страницы чтения (лендинг, лента, лидерборд). Авторизованные сценарии (создание
  кампаний, выплаты) нагружают БД сильнее — их надо тестировать отдельно, с тестовыми сессиями.
- Не проверяет платёжного провайдера и внешние API (YouTube/VK/ЮKassa) под нагрузкой.
- Один регион (Vercel `lhr1`). Глобальная аудитория добавит сетевую задержку.

## 6. Быстрая альтернатива без установки k6

```bash
npx autocannon -c 200 -d 30 https://ВАШ-ПРОД-URL/campaigns
```
`-c 200` = 200 одновременных соединений, `-d 30` = 30 секунд. Даёт req/sec, задержки и ошибки.
Для грубой прикидки одного самого тяжёлого пути.
